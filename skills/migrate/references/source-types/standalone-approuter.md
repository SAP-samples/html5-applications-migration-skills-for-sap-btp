# Standalone Approuter Source App Structure

## Load trigger

Load during Phase 1 baseline analysis when the source type is identified as `standalone-approuter`.

---

## What Is a Standalone Approuter?

A **standalone approuter** is an MTA module of type `approuter.nodejs` that is deployed as a dedicated Cloud Foundry application. It differs from the *managed approuter* (SAP WorkZone / html5-apps-repo pattern) in that:

- It owns and runs the `@sap/approuter` package directly (no SaaS subscription to a shared approuter)
- Static HTML5 files are served **directly from the approuter's file system** via `localDir` routes — no `html5-apps-repo` or `app-front` service is involved in the source
- Auth configuration is owned by the approuter module (bound to XSUAA directly)
- Backend APIs are reached via named `destinations` injected through the MTA `provides`/`requires` mechanism

This pattern is common in CAP + XSUAA applications generated by SAP Business Application Studio or the CAP CLI.

## Typical MTA Structure

```
mta.yaml
├── modules
│   ├── <app>-srv              ← CAP Node.js backend (type: nodejs)
│   │   provides:
│   │   └── srv-api            ← destination consumed by approuter
│   │   requires: [<app>-auth, <app>-db]
│   │
│   ├── <app>-db-deployer      ← HDI deployer (type: hdb)
│   │   requires: [<app>-db]
│   │
│   └── <app>                  ← STANDALONE APPROUTER (type: approuter.nodejs)
│       path: app/router        ← contains xs-app.json
│       requires:
│       ├── srv-api            ← destination injection (group: destinations)
│       │   group: destinations
│       │   properties:
│       │     name: srv-api
│       │     url: ~{srv-url}
│       │     forwardAuthToken: true
│       └── <app>-auth
│
└── resources
    ├── <app>-auth (xsuaa / application)     ← XSUAA service
    └── <app>-db   (hana / hdi-shared)       ← HANA HDI container
```

**Key identifiers:**
- Module `type: approuter.nodejs` — this is the definitive signal
- Module `path` points to a directory containing `xs-app.json`
- No `html5-apps-repo` resource anywhere in `mta.yaml`
- No `destination-content` module
- `xs-app.json` contains routes with `"localDir"` serving static content from the filesystem

## xs-app.json with `localDir` Routes

The distinguishing feature of this source type is `localDir` routes:

```json
{
  "authenticationMethod": "route",
  "welcomeFile": "/interaction_items/webapp/index.html",
  "routes": [
    {
      "source": "^/app/(.*)$",
      "target": "$1",
      "localDir": ".",                               ← serves files from the approuter's path
      "cacheControl": "no-cache, no-store, must-revalidate",
      "authenticationType": "xsuaa"
    },
    {
      "source": "^/appconfig/",
      "localDir": ".",
      "cacheControl": "no-cache, no-store, must-revalidate"
    },
    {
      "source": "^/user-api(.*)",
      "target": "$1",
      "service": "sap-approuter-userapi"
    },
    {
      "source": "^/(.*)$",
      "target": "$1",
      "destination": "srv-api",
      "csrfProtection": true,
      "authenticationType": "xsuaa"
    }
  ]
}
```

**`localDir` semantics**: The approuter serves files from a local directory relative to its own `path` in the MTA. The HTML5 app source files live **inside the approuter module's directory** (e.g., `app/router/`) rather than in a separate HTML5 module. This is fundamentally different from `html5-apps-repo` where built zip artifacts are uploaded to an external service.

## Static Content Location

In a standalone approuter, static content is typically located at the approuter module's `path`:

```
app/
└── router/                    ← approuter module path (contains xs-app.json)
    ├── xs-app.json
    └── <app-name>/            ← static HTML5 app files served via localDir
        └── webapp/
            └── index.html
```

Sometimes the UI apps are sibling directories to the router:

```
app/
├── router/
│   └── xs-app.json
└── <app-name>/
    └── webapp/
```

In this case the `localDir` in `xs-app.json` uses a relative path like `../` to reference parent directories.

## MTA Destination Injection (Group Pattern)

The standalone approuter uses a **group-based destination injection** pattern that is unique to this source type:

```yaml
# In the approuter module's requires:
requires:
  - name: srv-api
    group: destinations         ← injects as environment variable DESTINATIONS
    properties:
      name: srv-api             ← destination name used in xs-app.json
      url: ~{srv-url}           ← resolved from CAP srv module's provides
      forwardAuthToken: true
  - name: MyApp-auth
```

This translates to a `DESTINATIONS` env var on the approuter CF app at runtime:
```json
[{"name":"srv-api","url":"https://...","forwardAuthToken":true}]
```

In appFront, this pattern is replaced by `config.destinations` in the app-content deployer module.

## Key Differences from html5-apps-repo Source

| Aspect | Standalone Approuter | html5-apps-repo |
|--------|---------------------|-----------------|
| Static content location | Approuter filesystem (`localDir`) | External `html5-apps-repo` service |
| Content deployer module | None — content is part of the approuter module | `app-content` module uploads zip |
| Destination setup | MTA `requires` group injection | `destination-content` module or embedded creds |
| `xs-app.json` routing | `"localDir"` for static, `"destination"` for backend | `"service": "html5-apps-repo-rt"` for static |
| approuter ownership | App team owns and deploys the approuter | SAP WorkZone / BTP managed service |
| Scaling | Approuter scales independently | Shared managed approuter |

## Migration Complexity: Medium

The main migration work is:
1. **Extracting static content** from the approuter path into a buildable HTML5 module with a zip artifact
2. **Replacing the approuter module** with an `app-content` deployer module
3. **Converting `localDir` routes** to `"service": "app-front"` routes in `xs-app.json`
4. **Converting destination injection** from MTA `group: destinations` to `config.destinations` in the deployer

See `migration-guides/standalone-approuter-to-appfront.md` for the complete step-by-step guide.
